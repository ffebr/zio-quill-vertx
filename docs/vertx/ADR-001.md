# ADR-001: native Vert.x PostgreSQL с неизменённым QDSL

Статус: направление принято на основании уточнения пользователя; implementation contracts и тесты ещё предстоит реализовать.

## Решение и границы

Пользователь разрешил изменить слой подключения и контекст. Приоритет — сохранить Quill QDSL, чтобы не переписывать запросы проекта. Прежнее требование сохранить DataSource/Connection/PreparedStatement/ResultSet и все публичные JDBC сигнатуры отменено этим уточнением. Требование native Vert.x без JDBC-драйвера/fallback остаётся.

Разрабатываем отдельный native PostgreSQL backend, проектное имя `quill-vertx-zio`. Старый `quill-jdbc-zio` остаётся неизменённым reference. Не подменяем одноимённые классы и не эмулируем JDBC interfaces.

## Сохраняем

- Query expression bodies: `quote`, `query`, `querySchema`, `lift`, `liftQuery`, mapped encodings на логических типах, композицию, filters/maps/joins/aggregates, options, actions/batch, returning и SQL infix в рамках возможностей PostgreSQL.
- NamingStrategy, модели, query/schema metadata и семантику PostgreSQL. Существующие engine/core/SQL AST, DSL и macros переиспользуем; не строим новый язык запросов.
- ZIO как effect runtime, ZStream как streaming API. Типы конкретного environment и resource могут измениться на границе подключения.
- Исходные query fixtures и expected results. Несовпадение результатов не исправляется переписыванием QDSL или ослаблением assertions.

## Разрешённая интеграционная миграция

- Dependency/import контекста, создание context/Vert.x pool, конфигурация, ZLayer и environment annotations.
- JDBC-specific пользовательские encoders/decoders, JDBC/vendor objects (например PGobject), ручные Connection/PreparedStatement/ResultSet операции: перевести в native codecs/raw SQL API. Это отдельный список миграции; не обещать нулевые изменения при наличии JDBC escape hatches.
- Ошибки и resource ownership нового native API фиксируются явно. Совпадение старого typed error API желательно там, где достигается без драйвера; это не причина внедрять JDBC shim.
- Quill quotations привязаны к context и должны перекомпилироваться с новым context. Нельзя обещать перенос ранее скомпилированного context-bound quote object без перекомпиляции. Изменение wiring/import владельца context разрешено; query expression остаётся тем же.

## Архитектура

Переиспользовать `ZioContext`, `SqlContext`, context verbs и SQL translation/macro abstractions. Не наследовать JDBC-specific `JdbcContextTypes`, `Encoders`, `Decoders` как transport контракт: они фиксируют JDBC row/session types.

Data-only `JsonValue`/`JsonbValue` сейчас объявлены в JDBC-ZIO модуле. Для их сохранения нужен согласованный lightweight shared types/package layout без зависимости native backend от JDBC-ZIO и без duplicate FQCN. Механическое выделение общих типов разрешено при сохранении их имён/поведения и неизменных regression expectations; оно не даёт права менять JDBC execution ради native тестов.

Внутренние parameter/row/session типы native; конкретные interfaces фиксирует T03. Native PostgreSQL client исполняет prepared queries; Future bridge подключает его к ZIO. Transaction scope владеет одной native connection и распространяет её на nested операции и stream. Native prepare возвращает native/Quill abstraction, а не синхронный JDBC statement.

Backend-level placeholder adaptation разрешена; слепая строковая подстановка не разрешена. Где возможно, использовать structured generation/idiom extension, сохраняя PostgreSQL SQL semantics и прежние query bodies. Формат placeholder протокола не равен изменению QDSL.

## Почему прежний блокер снят

Раньше требовалось сохранить произвольный DataSource и синхронные JDBC objects без драйвера. Теперь эти API разрешено менять в слое интеграции. Поэтому не требуется ни извлечение credentials из произвольного DataSource, ни vendor unwrap/JDBC proxy, ни синхронное ожидание native Future ради старых statements.

Остаются реальные задачи codec/data parity, transaction/cancellation/stream lifecycle и тестирования всей поддерживаемой QDSL поверхности. Они являются работой по реализации, а не основанием возвращать старый JDBC API как обязательный gate.

## Доказательства

Один corpus query expressions с одинаковыми ожиданиями исполняется на JDBC reference и native backend. Backend wiring, effect runner и native codec registration могут различаться и должны быть явно показаны. Эталонные тесты/ожидания не редактируются. Native tests дополнительно проверяют отсутствие драйвера/fallback, отмену и освобождение ресурсов. Закрытое приложение пока недоступно: библиотечный corpus не доказывает его интеграционный запуск.
