# Native Vert.x SQL compatibility

This guide describes the native execution backends in `quill-vertx-zio` and
separates implemented APIs from the integration evidence available so far. The
goal is to reuse Quill QDSL and SQL generation while replacing JDBC transport,
context wiring, and JDBC-specific codec callbacks. The QDSL expressions are
intended to remain unchanged in meaning; context-bound quotations must be
recompiled with the native context. This is not evidence of complete SQL
feature parity across vendors, a drop-in black-box proof, or validation of a
particular application.

## Contexts and pool builders

| Database | Context | Vert.x options | Owned pool layer | Caller-owned Vert.x layer |
| --- | --- | --- | --- | --- |
| PostgreSQL | `PostgresZioVertxContext` | `PgConnectOptions` | `VertxPool.live` | `VertxPool.fromVertx` |
| MySQL / MariaDB | `MysqlZioVertxContext` | `MySQLConnectOptions` | `VertxPool.mysql` | `VertxPool.mysqlFromVertx` |
| DB2 | `DB2ZioVertxContext` | `DB2ConnectOptions` | `VertxPool.db2` | `VertxPool.db2FromVertx` |

All pool builders take the driver's connect options and Vert.x `PoolOptions`,
and produce `ZLayer[Any, Throwable, io.vertx.sqlclient.Pool]`. The
`*FromVertx` forms also take a caller-owned `io.vertx.core.Vertx`; they close
the pool but leave that Vert.x instance open. The other forms scope and close
both Vert.x and the pool. Credentials and TLS are configured using the
corresponding Vert.x connect options. Database clients are native; there is no
JDBC execution path or fallback in this module.

The shared entry points and imports are the `zio.quill` context classes and
`zio.quill.context.vertx.VertxPool`. For example:

```scala
import io.vertx.mysqlclient.MySQLConnectOptions
import io.vertx.sqlclient.PoolOptions
import zio.quill._
import zio.quill.context.vertx.VertxPool

val ctx = new MysqlZioVertxContext(SnakeCase)
import ctx._
case class Person(name: String, age: Int)
val adults = ctx.run(query[Person].filter(_.age >= lift(18)))
val connect = new MySQLConnectOptions()
  .setHost("localhost").setPort(3306).setDatabase("application")
  .setUser("application")
val layer = VertxPool.mysql(connect, new PoolOptions().setMaxSize(10))
val application = adults.provideLayer(layer)
```

MySQL and MariaDB share the Vert.x MySQL driver, context, and pool builder.
Vert.x SQL client interfaces currently come from Vert.x 4.5.36; treat those
low-level interfaces as pinned implementation details.

DB2 uses the explicitly corrected `quill-vertx-db2-client` artifact. The
upstream 4.5.36 client declares CCSID 500 but uses CP1047, which breaks passwords
containing characters such as `!`. The corrected artifact changes that charset
to CP500, pins the upstream binary by SHA-256 and preserves its classes and
service resources. See the [artifact README](../../quill-vertx-db2-client/README.md).

## Migration boundaries

- Switch context imports/construction and `DataSource`/`Connection` layers to
  the native context and pool layer, then recompile context-bound quotations.
  Keep the QDSL expression and its intended meaning unchanged.
- Adapt custom JDBC `Encoder`/`Decoder` callbacks to the native tuple/row
  codec APIs. Existing logical `MappedEncoding` mappings remain usable where
  the native context has the corresponding scalar codec. JDBC callbacks that
  require `PreparedStatement`, `ResultSet`, or vendor `unwrap` are not
  compatible as-is; migrate them to native SQL client APIs.
- `ctx.VertxEncoder` receives `(index, value, tuple, connection) => tuple` and
  `ctx.VertxDecoder` receives `(index, row, connection) => value`. Indices are
  zero-based and encoders append bind parameters in order.
- `ctx.prepare(quotation)` creates an effectful reusable `VertxPreparedQuery`;
  its SQL uses the native placeholders and execution returns a Vert.x
  `RowSet[Row]`. Preparing does not execute SQL or hold a connection. Execution
  uses the current transaction when present. `ctx.probeAsync(sql)` is the
  effectful native replacement for the unsupported synchronous compile-time
  probe. `ctx.translate(quotation, options)` is synchronous diagnostic SQL;
  execution binds native parameters separately.
- `JsonValue` and `JsonbValue` retain their shared ZIO module names; native JSON
  codecs use zio-json and Vert.x JSON values rather than JDBC `PGobject`.

## Known backend-specific limits

- MySQL/MariaDB returning supports exactly one autogenerated INSERT key,
  implemented using the server-provided generated id. It does not implement
  returning arbitrary columns or multiple generated fields.
- MySQL/MariaDB and DB2 codec implementations map temporal values through UTC
  when the SQL type does not retain an offset. Applications with timezone-sensitive values should verify
  behavior at the migration boundary.
- PostgreSQL cancellation invokes Vert.x `PgConnection.cancelRequest`, which
  asks the server to cancel the query. For MySQL/MariaDB and DB2,
  interruption aborts the socket-backed connection. An aborted transport does
  not prove that the server acknowledged cancellation.
- Oracle is not a native backend here. Vert.x 4.5.36's Oracle client uses JDBC
  internally, which does not meet this module's native transport boundary.

## Validation evidence and how to run it

The following are the integration results reported for the current
implementation. A backend being implemented or having a runner does not by
itself establish compatibility.

| Backend | Evidence reported so far | Current limitation |
| --- | --- | --- |
| PostgreSQL 16.11 | 166 native tests / 29 suites passed on Scala 2.12.20 and 2.13.16 | Selected suite evidence, not exhaustive SQL or application coverage. |
| MySQL 8.4.7 | 21 tests / 4 suites passed on both Scala versions (native 7, shared People 10, shared returning 2, shared encoding 2) | Selected shared/native corpus; not exhaustive SQL coverage. |
| MariaDB 11.4.5 | 21 tests / 4 suites passed on both Scala versions | Selected shared/native corpus; not exhaustive SQL coverage. |
| DB2 LUW 11.5.8.0 | 21 tests / 3 suites passed on both Scala versions (native 9, shared People 10, shared encoding 2) | Uses the corrected native client; other DB2 server variants are unverified. |

Runner behavior:

- `./tools/vertx/test.sh` starts the PostgreSQL harness and runs a selected
  PostgreSQL-focused test set, not every module test.
- `./tools/vertx/test-sql.sh postgres|mysql|mariadb|db2` starts the
  selected database harness and runs matching test names.
- `./tools/vertx/test-sql.sh all` starts PostgreSQL, MySQL, MariaDB, and DB2 harnesses and runs `quill-vertx-zio/test`. It therefore needs all
  databases available and is not a PostgreSQL-only command.
- The scripts require sbt. `QUILL_VERTX_CLEAN=1` asks them to clean the module
  before running, which is useful after dialect edits because Quill embeds SQL
  at macro expansion time.

Compatibility claims should be updated as backend-specific native results
arrive. Existing JDBC backends and suites are outside this module's execution
path; their passing results do not establish native Vert.x behavior.

The full module suite passes 239 tests across 41 suites on each Scala version,
including 10 portable dialect and diagnostic tests, with no failures,
cancellations, ignored or pending tests. SQL Server was removed from the native
backend at the user's request, together with its context, client, tests and
harnesses. See [MULTI-SQL-VALIDATION.md](MULTI-SQL-VALIDATION.md) for commands,
retained history and dependency checks.
