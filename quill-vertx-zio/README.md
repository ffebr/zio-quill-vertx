# Native SQL, Vert.x and ZIO

This module reuses Quill QDSL and SQL generation through native Vert.x SQL
clients. It currently provides PostgreSQL, MySQL/MariaDB, and DB2
contexts. Connection wiring and JDBC-specific codecs change; query expressions
are intended to remain unchanged. There is no JDBC execution or fallback in
this module. This is not a claim of complete cross-database compatibility or a
drop-in, black-box validated application replacement. See
[`docs/vertx/MULTI-SQL-COMPATIBILITY.md`](../docs/vertx/MULTI-SQL-COMPATIBILITY.md)
for APIs, limits, and per-database evidence.

Fork packages use Maven group `io.github.ffebr` and this repository's GitHub
Packages registry. See [RELEASING.md](../docs/vertx/RELEASING.md) for the initial
alpha version, CI/CD and authenticated dependency setup.

## PostgreSQL wiring

```scala
import io.vertx.pgclient.PgConnectOptions
import io.vertx.sqlclient.PoolOptions
import zio.quill._
import zio.quill.context.vertx.VertxPool

val ctx = new PostgresZioVertxContext(SnakeCase)
import ctx._
case class Person(name: String, age: Int)

val adults = ctx.run(query[Person].filter(_.age >= lift(18)))
val config = new PgConnectOptions()
  .setHost("localhost").setPort(5432).setDatabase("application")
  .setUser("application") // Supply authentication through your own config/layer.
val layer = VertxPool.live(config, new PoolOptions().setMaxSize(10))
val application = adults.provideLayer(layer)
```

The other native contexts are `MysqlZioVertxContext` and `DB2ZioVertxContext`.
`VertxPool` offers matching `mysql` and `db2` builders. Each accepts its driver's connect
options and `PoolOptions` and returns `ZLayer[Any, Throwable, Pool]`. The
`*FromVertx` forms (`fromVertx`, `mysqlFromVertx`, `db2FromVertx`) additionally
accept a caller-owned `io.vertx.core.Vertx`.
Builders without `FromVertx` own a Vert.x instance and pool in the ZIO scope;
the borrowed-Vert.x variants own and close only the pool.

For example, MySQL and MariaDB use the same Vert.x MySQL client and context:

```scala
import io.vertx.mysqlclient.MySQLConnectOptions
import io.vertx.sqlclient.PoolOptions
import zio.quill.context.vertx.VertxPool

val ctx = new MysqlZioVertxContext(SnakeCase)
val options = new MySQLConnectOptions()
  .setHost("localhost").setPort(3306).setDatabase("application")
  .setUser("application")
val layer = VertxPool.mysql(options, new PoolOptions().setMaxSize(10))
```

Configure driver options for the target server, including credentials and TLS,
using the corresponding Vert.x `PgConnectOptions`, `MySQLConnectOptions`,
or `DB2ConnectOptions`. Build the layer around the
application lifetime rather than once per query. Context APIs require a native
Vert.x `Pool` environment; native results use `ZIO[Pool, Throwable, A]` and
streams use `ZStream[Pool, Throwable, A]`.

## Migration and behavior

- Replace context imports/construction and DataSource/Connection layers with a
  native context and pool layer. Recompile context-bound quotations with that
  context. Keep `quote`, `query`, `querySchema`, `lift`, `liftQuery`, and query
  or action bodies unchanged in intent.
- Adapt custom JDBC Encoder/Decoder callbacks to native Tuple/Row codecs.
  Logical `MappedEncoding` mappings can remain unchanged when a scalar codec
  exists. JDBC statement/row callbacks and vendor `unwrap` APIs are not
  emulated.
- `JsonValue` and `JsonbValue` retain their public names in the shared ZIO
  module. Native JSON codecs use zio-json and Vert.x JSON values, not
  `PGobject`.
- The synchronous compile-time `probe` API is unsupported. Use the effectful
  `ctx.probeAsync(sql)` to prepare/validate SQL through a native connection.
- `ctx.prepare(quotation)` returns an effect producing a reusable
  `VertxPreparedQuery`. Its `sql` contains native placeholders and its
  `execute` effect returns a Vert.x `RowSet[Row]`; preparation alone neither
  executes SQL nor retains a connection. Execution participates in the current
  `ctx.transaction` if present. Batch preparation produces a list of these
  operations. `ctx.translate(quotation, options)` returns diagnostic SQL
  synchronously, including pretty printing and optional lift rendering; runtime
  execution separately binds native parameters.
- PostgreSQL cancellation calls the server-side `PgConnection.cancelRequest`.
  MySQL/MariaDB and DB2 interrupt an in-flight operation by
  aborting its socket-backed connection. A transport abort does not establish
  that the server acknowledged cancellation.
- MySQL/MariaDB returning supports one autogenerated INSERT key. It does not
  support arbitrary returned columns or multiple generated fields.
- MySQL/MariaDB and DB2 codecs use UTC when representing temporal values in SQL
  types that carry no offset. Treat these conversions as part of the native codec
  contract when migrating timezone-sensitive data.

Prefer logical mappings for custom scalar types, for example
`MappedEncoding[UserId, Long](_.value)` and
`MappedEncoding[Long, UserId](UserId.apply)`. For direct native callbacks,
`ctx.VertxEncoder` accepts `(index, value, tuple, connection) => tuple` and
`ctx.VertxDecoder` accepts `(index, row, connection) => value`. Indices are
zero-based; encoders append parameters in order.

The native module uses Vert.x 4.5.36. Its lower-level Vert.x SQL client
interfaces are pinned implementation dependencies; application integrations
should prefer the context and pool builders documented here.

## Local validation

From the repository root with JDK 17 and sbt available:

```bash
./tools/vertx/test.sh
```

This starts the pinned local PostgreSQL harness and runs the module's selected
PostgreSQL-focused test suites. `tools/vertx/test-sql.sh` selects database
profiles (`postgres`, `mysql`, `mariadb`, `db2`, or `all`); the
`all` profile starts all harnesses and runs the entire module test suite. These
commands require sbt. Test scripts and current evidence are documented in the
multi-SQL compatibility guide. The native test module has no JDBC test
dependency; PostgreSQL original suites are separate reference checks. Never
add JDBC execution to the native path to make a test pass.

## Changing SQL generation

Quill embeds static SQL during macro expansion. After changing a dialect's
implementation, sbt may retain compiled consumer quotations whose source did
not change. Clean the module before accepting SQL-generation changes:

```bash
sbt quill-vertx-zio/clean quill-vertx-zio/test
```

With the PostgreSQL helper, `QUILL_VERTX_CLEAN=1 ./tools/vertx/test.sh` performs
that clean first. This is a build-cache concern; query expressions and
assertions must remain unchanged.
